# Architecture — Rarity Pipeline & Data Model

How a species' "rarity pill" (e.g. *Likely · 30-60%*) is produced, where every
data file fits, and **"I want to change X — where do I go?"**. Read this before
touching rarity/season/time-of-day logic.

---

## 1. The big picture: build-time vs runtime

```
                BUILD TIME (scripts/, ~3h, weekly)            RUNTIME (browser)
  eBird ─┐
  iNat  ─┼─► buildWildlifeCache.js ─► wildlifeCache.js ─► splitCache.js ─► Primary/Tier2/Tier3.js
  NPS  ─┘    (charisma corr.,         (one 24MB file)      (3 lazy-loaded tiers)        │
              NPS abundance gate,                                                       ▼
              dedup, slim)                                              wildlifeCacheLoader.js
                                                                       (applies runtime passes)
                                                                                        │
                                                                                        ▼
                                                                       App.jsx computeEffectiveRarity()
                                                                       + apiService applyRarityOverride()
                                                                                        │
                                                                                        ▼
                                                                                 the rarity pill
```

- **Build** runs in GitHub Actions (`.github/workflows/weekly-rebuild.yml`), sharded ×4.
  It writes only the 4 generated cache files. `slim()` strips `_debug`/`obsCount`
  before bundling — **runtime has no obs counts**, only `raritySource`.
- **Runtime** never calls the build scripts. It loads the static cache and layers
  hand-curated corrections on top.

## 2. Runtime rarity = layered. Order matters.

`wildlifeCacheLoader.js` runs these passes on every tier load (primary at import,
then `loadTier2`/`loadTier3`), **in this order**:

1. `_indexSciNames` / `_backfillSciNames` — fill missing scientific names via
   cross-park index + `SPECIES_NAME_ALIASES`.
2. `_dedupeWithinPark` — collapse same-species duplicates (keeps richer entry).
3. `_patchMissingFlagshipSpecies` — inject species the build pipeline drops
   (`missingSpeciesPatches.js`). Idempotent: skips if already present.
4. `_applyZoneOverrides` — merge `zoneOverrides.js` into `animal.zones`.
5. `_autoDeriveZoneSeasonal` — fill `seasonFrequencies` for zones lacking them.
6. `_applyRuntimeRarityPatches` — name-mismatch tier corrections (e.g. cache
   stores "American Black Bear", override targets "Black Bear").
7. `_applyConfidence` — derive the confidence dot from the **final**
   `raritySource` (runs last because 4/6 can change it).

Then per-render, `App.jsx::computeEffectiveRarity(animal, ctx)`:

1. **Zone** freq (if a zone is selected) → else **season** freq → else **park** freq.
2. **Effort** rescale (`VISITOR_EFFORT`: expert 1.0 / casual 0.65 / drive 0.35).
3. **Activity-period × time-of-day** rescale (`TIME_OF_DAY_MULTIPLIER`).
4. **Detectability ceiling** (`detectability.js`) — caps cryptic/hard species
   *only when no zone is active* (zones already encode visible-context behavior).
5. **Destination boost** (`applyDestinationBoost`) — park-level pill may rise ≤1
   tier if a high-frequency front-country zone exists.
6. Re-map frequency → tier.

And `apiService.js::applyRarityOverride(park, species, tier)` applies the
hand-curated `RARITY_OVERRIDES` table (anchor-calibrated; wins on tier).

> **Rule of thumb:** zone data > season data > park data; curated overrides
> beat pipeline output; detectability only caps the park-level (no-zone) pill.

## 3. Data files — what each controls

| File | Controls | Safe to hand-edit? |
|---|---|---|
| `src/data/wildlifeCache*.js` | Auto-generated species lists + base rarity | **No** — regenerated by rebuild |
| `src/services/apiService.js` → `RARITY_OVERRIDES` | Park-level tier corrections (anchor-calibrated) | Yes |
| `src/data/zoneOverrides.js` | Per-zone rarity + `seasonFrequencies` + `peakWindow` | Yes |
| `src/data/missingSpeciesPatches.js` | Species the build silently drops | Yes (audit-driven) |
| `src/data/detectability.js` | Cryptic/hard ceilings (case-insensitive lookup) | Yes |
| `src/data/speciesMetadata.js` | Activity period, effort/time multipliers, `computeConfidence` | Yes |
| `src/data/parkZones.js` | Zone definitions + front-country access tier | Yes |
| `scripts/rarityAnchors.json` | 206 ground-truth calibration anchors (both tiers) | Yes |
| `src/data/sightingFeedback.js` | Anonymous visitor 👍/👎 ground-truth log | Logic only |

## 4. Safety net (run before every push; gates PR-checks CI)

```
node scripts/testRarityPipeline.js        # 48 regression assertions
node scripts/auditDataQuality.js          # 8 audits (override/zone/anchor targets
                                          #  exist, freq-tier consistency, detectability
                                          #  orphans, case-only key mismatches…)
node scripts/calibrateAgainstAnchors.js   # mean tier distance vs 206 anchors (≤0.5 gate)
node scripts/auditTopNDropouts.js         # silent build-pipeline dropouts (target: 0)
npm run build                             # production build must pass
```

Current healthy baseline: **48/48 tests, 0 audit critical, calibration ≈0.02,
0 silent dropouts, build OK.** If calibration jumps, an override/anchor is
miscast; if Audit 8 fails, a table key's casing drifted from the cache.

## 5. The weekly rebuild — and why it's bulletproof now

`.github/workflows/weekly-rebuild.yml`: preflight → 4 rebuild shards →
merge job (mergeShards → splitCache → enrich → build → validate → **auto-merge**).

Runs #10/#11 lost full 3h rebuilds to a push race. The merge step is now
**branch-first**: it force-pushes the rebuild to bot-owned
`automated/cache-rebuild` (zero contention — always succeeds) *before*
opportunistically fast-forwarding `main` (12-attempt backoff), and falls back
to a PR if the race is lost. **Data loss is structurally impossible.**

> Gotcha: the PR fallback needs *Settings → Actions → General → "Allow GitHub
> Actions to create and approve pull requests"* = ON. If off, the rebuild is
> still safe on the branch (a warning says so) — open the PR manually.
>
> Recovery without a re-run: download the 4 `cache-shard-*` artifacts →
> `shards/` → `node scripts/mergeShards.js shards/ && node scripts/splitCache.js`.

## 6. The accuracy feedback loop (long game)

Anchors hand-cover ~0.6% of entries. `sightingFeedback.js` logs anonymous
visitor verdicts with full context (park/species/season/zone/effort/time +
the predicted tier). Export via the D-key debug panel → `summarizeSightings()`
gives an empirical seen-rate per bucket → fold high-`n` buckets back into
`rarityAnchors.json` / `RARITY_OVERRIDES`. This is the only path to accuracy
beyond expert curation.

## 7. "I want to change X" quick map

- **A species shows the wrong tier at a park** → `RARITY_OVERRIDES` (apiService.js).
  Add an anchor in `rarityAnchors.json` so it's regression-guarded.
- **Wrong tier only in a specific area/season** → `zoneOverrides.js`.
- **Species missing entirely at a park** → confirm with `auditTopNDropouts.js`,
  then add to `missingSpeciesPatches.js`.
- **Common species over-promised (e.g. cryptic)** → `detectability.js`
  (`hard` caps at *likely*, `cryptic` at *unlikely*).
- **Wrong "best time of day"** → `ACTIVITY_PERIOD_EXACT` / `_KEYWORDS` in
  `speciesMetadata.js`.
- **Confidence dot wrong** → `computeConfidence` raritySource mapping.
- **Bulk data stale** → trigger the weekly rebuild (don't hand-edit cache files).
